## 用户目标与 MQTT 合约（已获得温度实测帧，仍待实车验证）

2026-10-17 用户实测巴法温度指令：`on#1#26#0#0#0`。将第 3 字段按十进制摄氏温度解释，当前严格接受 `on#1#<15..31>#0#0#0`。**运行时间由 APP 内的选择器决定**，默认 30 分钟，可设置 10、15、20、25、30 分钟；本地 `SharedPreferences` 保存，下次打开自动恢复。APP 手动空调操作和小爱 MQTT 调温共用这一设置，分别编码为 `timeSpan=1..5`，不从 MQTT 消息读取时长。

**最新开发源代码**：[动态协议/界面补丁](./patch_dynamic_upstream.py)、[MQTT 解析器](./source/XiaodiCommandParser.kt)、[30分钟空调参数生成器](./source/ClimateControlParams.kt)、[GitHub Actions 构建](../../../.github/workflows/byd-assistant-v4.yml)。旧 `patch_upstream.py` 为不再维护的固定26℃实验稿，**不要使用**。

本地控制 UI 新增：温度－、温度＋、运行时间选择、启动空调、关闭空调。所有按钮使用已登录比亚迪会话及原存储 PIN，不会在语音指令中传递凭据。
米家已将昵称“**小迪**”的巴法云虚拟设备修改为空调类设备。原有主题不应凭截图重猜，App 必须使用用户在巴法云复制的准确 Topic。空调虚拟设备传送的实际 MQTT payload 需要在巴法控制台采集验证。

### 安全策略
- 任何未知/超范围 payload 不触发车控。MQTT retained、duplicate、重复命令仍应拒绝。
- 当前 `on`→解锁、`off`→锁车映射不能在没有迁移测试的情况下被悄悄替换。
- 将空调型 `on` 映射为“整车启动”之前，必须拿到可验证的专门远控 API；启动失败不得自动转换成解锁操作。
- `CLOSEAIR` 不是发动机熄火命令；UI、语音反馈、更新日志均不得将其称为已成功熄火。
- 无需提交 BYD 账号密码、控制 PIN、VIN、MQTT UID 或签名私钥。

## APK 覆盖安装的硬条件
现有原版 APK `applicationId = dev.vehiclebridge.byd`（以实际设备安装包为准）。
**Android 覆盖安装需要 applicationId 一致、签名证书一致，以及更高的 versionCode**。
上游源码可复制包名，但不能复制原开发者的签名；不同签名的 APK 即便包名相同，Android 仍会拒绝作为更新安装。先核对当前手机 APK 的签名指纹/安装来源及是否有原签名密钥。不能假设 GitHub Actions 的 debug keystore 等于现有原版签名。
若签名不可获得，不能同时保证“不卸载旧 App”和“完全替代原 APK”。不得诱导用户上传私钥或账号。

## 2026-10-18 扩展需求：车辆信息、蓝牙自动化、漏锁提醒

### 安全变更：空调设备不得解锁车门
- 对于同一个米家/巴法空调设备，裸 `on` 与 `on#1#温度#0#0#0` 均为请求启用空调 `OPENAIR`，**不能**映射为 `OPENDOOR`。裸 `on` 使用 APP 已保存的目标温度/时长。
- `off` 现存语义与“关闭空调”及“锁车+CLOSEAIR”冲突；在未确认实际米家操作帧前，产品不应声称两种关操作能可靠区分。关闭空调应走独立 APP 按钮或额外 Topic。
- 控制云端 ACK 不是门锁状态。严禁仅凭最近一次 `LOCKDOOR` 成功就声称防盗状态正常。

### 车辆信息页（非语音）
用户提供的参考图包含：低压供电系统、动力电池、动力系统健康状态，总里程、EV/HEV里程、近50km能耗、累计能耗、整车/动力模式、OK指示灯、行驶状态、车速、功率、发动机冷却液温度。
- 新增 [VehicleStatusPresenter.kt](./source/VehicleStatusPresenter.kt)：对现有中国区接口返回的明确字段进行显示，尚无数据的显示“未提供”。不得将健康状态伪造成“正常”。
- 当前上游 `VehicleTelemetry` 只明确解析里程、电量、续航、胎压、部分能耗；其他字段需要专门适配响应映射。刷新时间标注云端上报时间，不冒充实时车端状态。
- App UI 复用现有“我的车辆 → 车辆数据卡片”，本开发补丁打开状态卡片并接入手动刷新入口。

### 蓝牙自动化（不接小爱、不默认启用）
UI 计划三项独立开关：①已配对的**指定车辆蓝牙设备**连接后请求解锁；②该设备断开后请求锁车；③可能未锁提醒及提醒延迟（建议默认5分钟，用户可调）。
- 新增 [BluetoothActionDecider.kt](./source/BluetoothActionDecider.kt) 及 [BluetoothActionDeciderTest.kt](./source/BluetoothActionDeciderTest.kt)：仅对准确匹配已选蓝牙设备的连接/断开事件给出决策，开关默认关闭，抑制重复及短时间重复事件。
- **当前未接入可持续监听的 Android 蓝牙后台服务、Android 12+ BLUETOOTH_CONNECT 动态授权、配对设备选择 UI、VIN/PIN 验证和实际车控分发；所以自动锁/解锁仍未可用。** 不得在用户界面将其显示为已生效。
- 蓝牙连接≠本人靠近或授权；蓝牙断开≠本人已离车。断线/系统省电/耳机切换可能造成事件误判，需要用户明确授权、冷却时间、车速/状态安全限制以及实车测试。
- 漏锁提醒需要独立可靠的**车辆锁状态 API**。当前上游 `VehicleTelemetry` 明确标识非真实锁状态来源，所以 [PossibleUnlockedReminder](./source/BluetoothActionDecider.kt) 只能提醒“可能未锁车”；在真实锁状态接入前不能宣称“已确认未锁”。
- 通知与振动依赖 Android 通知授权和振动权限；后台定时器需结合前台服务或合规调度，避免后台被系统杀死后误以为提醒仍运行。

### 安装与测试边界
本次新增只读车辆状态展示逻辑、蓝牙决策引擎与单元测试，**不是蓝牙联动完整交付**。任何包含自动解锁功能的版本在启用前都必须通过 Android 权限、配对设备验证、锁状态边界和实车测试。不能宣称已经构建或已可无损覆盖安装。

## 2026-10-18 用户最终确认：同一空调 Topic 的三条精确映射（取代此前建议）
| 实际 MQTT payload | 对应 BYD API | 是否解锁 |
| --- | --- | --- |
| `on` | `OPENDOOR`：解锁 | **是** |
| `off` | `LOCKDOOR`：锁车，确认成功后再 `CLOSEAIR`：关闭空调 | **否** |
| `on#1#26#0#0#0` 等六段调温帧 | `OPENAIR`：按实际温度启动空调，时长取 App 已保存设置 | **绝不解锁** |

以上是当前唯一有效路由契约。早先“裸 on 也开空调”的建议已撤销；**不再要求单独 Topic**。这三种 payload 可以根据原始消息完全区分。对于仅“关闭空调”保留 App 本地 `CLOSEAIR` 按钮，米家说“关闭小迪”意味着锁车加关闭空调。

### 蓝牙设备名称配置
用户提供的实际蓝牙名称为 **秦Plus**。App 设置页新增「车辆蓝牙名称」输入框和「保存蓝牙名称」按钮，默认显示秦Plus，本地保存于 `xiaodi_bluetooth/vehicle_name`。此项目前只是配置 UI，**尚未实际启动后台蓝牙监听/自动车控**。为避免同名设备误解锁，未来事件匹配还必须绑定到用户授权、已配对的设备地址（或可验证的系统设备标识），而不是仅凭蓝牙名称。
